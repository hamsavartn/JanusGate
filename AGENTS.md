## Environment rules (constraint C1–C2)

- Python is ONLY `.venv/Scripts/python.exe` (Windows venv). Never `pip install` globally, never `python -m pip` with the system interpreter.
- Install new packages only into the venv, only if truly needed, and add them to `requirements.txt` in the same change.
- Nothing is written outside `C:\Users\ASUS\Desktop\Forge_hacks\agent-sentinel`. No global config, no `--global` git flags, no home-directory state.
- Shell is Git Bash on Windows: use `/c/Users/ASUS/...` paths in bash, `C:\...` in tool configs.

## Secrets (constraint C3)

- Secrets live only in `.env` (gitignored). Template: `.env.example`.
- NEVER print secret values into logs, files, commits, or chat. Refer to them by name only.
- `GEMINI_API_KEY` — primary LLM + embeddings. `FEATHERLESS_API_KEY`, `AGENTBOXD_API_KEY` — sponsor integrations (optional; system degrades gracefully without each).

## Code conventions

- Backend: FastAPI + Pydantic schemas in `backend/schemas.py` (single source of truth for shapes).
- Every detection layer lives in `backend/engine/`, is independent, and returns structured data; `sentinel_core.py` merges them. A layer failing must degrade to `None`/skip, never raise.
- All new API endpoints: add schema models, then a test in `tests/`.
- Comments explain constraints/intent, not mechanics. Docstrings at module top.
- No dead code, no placeholder TODOs without an issue note in `docs/PROJECT_BLUEPRINT.md` §10.

## Honest-metrics rule (constraint C7)

- The dev corpus (`backend/engine/corpus.py`) is co-designed with the rules — 100% on it is expected and must always be disclosed as such.
- The eval set (`evals/payloads_eval.py`) is the honest number. Never tune rules/thresholds against eval payloads; tune on dev only. State methodology wherever a metric is published.
- Every metric in README/Devpost must be regenerated by `evals/run_eval.py` before submission.
